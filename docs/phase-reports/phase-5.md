# تقرير المرحلة 5 — الأطراف والمبيعات والمشتريات والخزينة

**التاريخ:** 2026-11-08
**الحالة:** مكتملة ومتحقق منها

## النطاق المنجز

### قاعدة البيانات
- 15 نموذجاً جديداً (tenant-scoped، مفاتيح مركبة `[tenantId, id]`):
  - `parties` — طرف موحّد `CUSTOMER|SUPPLIER|BOTH`: رمز، اسمان، رقم ضريبي، هاتف، حد ائتمان، شروط سداد، علم عميل نقدي
  - `cash_boxes` / `bank_accounts` — صناديق وحسابات بنكية، كل منها مرتبط بحساب دفتري (`accountId`)
  - `sales_invoices` + `sales_invoice_lines` — فاتورة مبيعات نقدية/آجلة، تفقيط (net/tax/grand)، `paidAmount`
  - `purchase_invoices` + `purchase_invoice_lines` — فاتورة مشتريات مع رقم/تاريخ فاتورة المورد
  - `sales_returns` + lines / `purchase_returns` + lines — مرتجعات مرتبطة بفاتورة أصلية
  - `goods_notes` + lines — `GRN` (استلام) / `GIN` (صرف) مع `unitCost` للـ GRN
  - `receipts` / `payments` + `allocations` — سندات قبض/صرف مع تخصيص على فواتير
- enums: `PartyType`, `PaymentType`, `GoodsNoteType`
- الترحيل: `20261108201338_phase5_parties_documents` — يشمل backfill للحسابات الجديدة (`5103 مشتريات`، `2104 بضاعة مستلمة غير مفوترة`)، الـ mappings، وتسلسلات المستندات للسنوات المالية الموجودة
- كل النماذج مسجلة في `TENANT_MODELS` → عزل تلقائي (تم اكتشاف وإصلاح ثغرة عزل قبل الالتزام).

### خريطة الحسابات والتسلسلات الجديدة
- مفاتيح جديدة: `PURCHASES` → `5103`، `GOODS_RECEIVED_NOT_INVOICED` → `2104`
- بادئات مستندات جديدة: `SI, SR, PI, PR, RV, PV, CT, GRN, GIN, RC, PY`

### الوحدات
- **`platform/shared`**: `DocumentSupportService` (سياق المستأجر/الشركة، mappings، إعادة محاولة deadlock، ترقيم المستندات) + `invoice-math.ts` (حساب net/tax/grand بتقريب 3 خانات، خصم نسبة مئوية).

### المبيعات (`platform/sales`)
- فاتورة: مسودة → ترحيل في معاملة واحدة:
  - نقدي: `Dr` حساب صندوق/بنك مختار بالقيمة الإجمالية
  - آجل: `Dr` حساب العملاء (`CUSTOMERS_CONTROL`)
  - `Cr` حساب المبيعات بالصافي، `Cr` ضريبة المخرجات بالضريبة
  - `Dr COGS / Cr INVENTORY` بتكلفة متوسط التكلفة المرجّح لكل سطر مخزون
- خدمات (`SERVICE`) لا تؤثر على المخزون.
- المرتجع: حركات مخزون عكسية (IN) + قيد `SALES_RETURNS`/ضريبة + استرداد نقدي أو تخفيض ذمة (`paidAmount`/`grandTotal` يُدار).
- الترحيلات عبر `PostingService` — فترات مفتوحة، حسابات قابلة للترحيل، ترقيم gapless `SI`/`SR`.

### المشتريات (`platform/purchases`)
- فاتورة: نقدي/آجل بنفس النمط — `Dr` مخزون (للأصناف المخزنية) أو `Dr` مشتريات (للخدمات)، `Dr` ضريبة مدخلات، `Cr` موردين أو صندوق/بنك.
- تدعم `supplierInvoiceNo`/`supplierInvoiceDate`.
- المرتجع: حركة OUT بتكلفة متوسط التكلفة الحالية (الدفتر لا يحفظ تكلفة سطر الشراء الأصلي — موثّق) + قيد `PURCHASES`/ضريبة مدخلات عكسي.
- المستودع اختياري عند غياب أسطر مخزنية.

### إشعارات البضاعة (`platform/goods-notes`)
- `GRN`: حركة IN + `Dr INVENTORY / Cr GOODS_RECEIVED_NOT_INVOICED` (حساب تسوية 2104).
- `GIN`: حركة OUT + قيد مقابل (مخزون ↔ حساب خروج/مصروف حسب الحالة — حالياً يقابل حساب المخزون عبر حسابات التسوية).
- لا تؤثر على `paidAmount` — التسوية مع الفواتير مسؤولية المستخدم/مرحلة لاحقة.

### الخزينة (`platform/treasury`)
- صناديق وبنوك: CRUD + ربط إلزامي بحساب دفتري نشط؛ الحساب المرتبط لا يتغير بعد الإنشاء.
- سند قبض: `Dr` حساب الصندوق/البنك / `Cr` عملاء أو موردين + ضريبة إن وُجدت — مع `allocations` اختيارية على فواتير مبيعات مفتوحة (`paidAmount` يُحدَّث).
- سند صرف: العكس — `Cr` صندوق/بنك، `Dr` موردين (أو حساب مصروف للتسديد المباشر بدون طرف).
- التخصيص يتحقق: نوع الطرف، نوع المستند (`SALES_INVOICE` للقبض، `PURCHASE_INVOICE` للصرف)، عدم تجاوز المتبقي (`grandTotal − paidAmount`)، والعملة.

### الواجهة (`apps/web`)
- صفحات جديدة في مجموعة «المبيعات والمشتريات»: **الأطراف**، **المبيعات** (فواتير + مرتجعات)، **المشتريات** (فواتير + مرتجعات)، **إشعارات البضاعة** (GRN/GIN)، **الخزينة** (صناديق/بنوك/قبض/صرف).
- `InvoiceLinesGrid` — شبكة فواتير: صنف/كمية/سعر أو تكلفة/خصم + أعمدة محسوبة (صافي/ضريبة/إجمالي)، تنقّل Enter بنفس نمط data-grid (يسار→يمين، لفّ للصف التالي، سطر جديد من آخر خلية).
- نمط Odoo: قوائم → عرض/نموذج بملء الشاشة؛ المسودات قابلة للتعديل والترحيل/الحذف، والمرحّل غير قابل للتعديل (التصحيح عبر مرتجع/عكس).
- i18n كامل ar/en.

## القرارات
- **طرف موحّد** للعملاء والموردين (`partyType` + `BOTH`).
- **المستندات المرحّلة غير قابلة للتعديل** — التصحيح عبر مرتجعات وعكس (معيار محاسبي).
- مرتجع المشتريات يخرج بمتوسط التكلفة الحالية وليس تكلفة سطر الشراء الأصلي (قيد دفتر الحركات).

## التحقق
- `pnpm --filter api test` — **8 suites / 67 tests** كلها خضراء، منها `phase5.e2e.spec.ts` (12 اختباراً: دورة فاتورة شراء/بيع كاملة، مرتجعات، GRN/GIN، سندات مع تخصيص، عزل المستأجرين).
- typecheck + lint + build للـ API والـ web نظيفة؛ vitest للـ i18n ناجح.
- تحقق حي على `erp_dev`: `PI-FY2026-000001`، `SI-FY2026-000001`، `GRN-FY2026-000001`، `RC-FY2026-000001` كلها مرحّلة بمخزون + قيود متوازنة.
- api-client أُعيد توليده (95+ مساراً).

## ملاحظات للمراحل القادمة
- JoFotara: إرسال الفواتير electronic + حقول الضريبة الإلزامية.
- تسوية GRN مع فواتير الشراء (3-way matching) غير منفذة — الحساب 2104 يبقى مفتوحاً حتى الفاتورة.
- الجرد الدوري/الدائم: التنفيذ الحالي perpetual عبر دفتر الحركات؛ التبديل الدوري يحتاج إعداداً على مستوى الشركة.

## إغلاق فجوات المرحلة 5 (2026-11-09)

مراجعة التقرير قبل بدء المرحلة 6 (القسم 17: «لا تبدأ مرحلة قبل اجتياز اختبارات قبول المرحلة
السابقة») أظهرت أن السيناريوهات الذهبية لم تُكتب كاختبارات، وأن `BranchGuard` غير منفذ، وأن
بنود القبول لم تُسجل كلٌ بحالته (القسم 22). أُغلقت على الفرع `phase-5-gaps`.

### إصلاحات كشفتها الاختبارات
- **المتبقي على الفاتورة (س10):** واجهة الفاتورة لم تكن تُرجع المتبقي، فكانت شاشة الخزينة تعرض
  `grand − paid` (37.120) بدل `grand − paid − المرتجعات الدائنة` (27.840) وتقترح تخصيصاً يرفضه
  الخادم. أُضيف `outstandingAmount` مشترك، وتُرجع الفواتير `creditedAmount` و`outstanding`،
  ويستخدمهما فحص التخصيص وشاشة القبض.
- **صلاحية الفرع:** `BranchGuard` + `X-Branch-Id` + محوّل فروع في الواجهة؛ الفواتير تأخذ فرعها من
  السياق، والترحيل يُرفض بـ `BRANCH_NOT_ALLOWED`؛ المرتجعات تتبع فرع الفاتورة الأصلية.
