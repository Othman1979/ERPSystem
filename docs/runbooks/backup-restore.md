# دليل النسخ الاحتياطي والاستعادة

المرجع: BUILD_PLAN §14-10 وADR-010 (§4 و§10.2). نسخة يومية لقاعدة البيانات والمرفقات معاً، واختبار
استعادة شهري موثق.

## ما الذي يُنسخ
- **مجلد واحد لكل نسخة** تحت `BACKUP_DIR`، اسمه `backup-YYYYMMDD-HHmmss` بتوقيت UTC، وفيه:
  - `database.sql.gz`: القاعدة كاملة بكل المستأجرين. لقطة واحدة متسقة (`mysqldump --single-transaction`)،
    دون قفل الجداول.
  - `storage.zip`: كل ما في `STORAGE_DIR`، وهو اليوم شعارات الشركات.
  - `manifest.json`: بصمة sha256 وحجم كل ملف، وعدد الـ migrations وآخرها، وإصدار الخادم.
- **النسخة الناقصة لا تُعتبر نسخة.** تُكتب في `.partial-…` ولا تأخذ اسمها إلا بعد اكتمالها، والتشغيل الفاشل
  يحذفها.
- **كلمة مرور القاعدة لا تظهر في سطر الأوامر.** تُكتب في ملف خيارات مؤقت (`--defaults-extra-file`)
  ويُحذف بعد التشغيل.
- **الصلاحيات:** المجلد `0700` والملفات `0600`، لأن النسخة تحمل بيانات كل المستأجرين. على Linux لا
  يقرؤها إلا حساب التطبيق.
- **حد معروف:** القاعدة تُفرَّغ أولاً، ثم تُضغط المرفقات بعدها بثوانٍ.
  - إذا استبدل مستخدم شعاره بين الخطوتين، قد تشير النسخة إلى ملف غير موجود فيها. `backup-verify` يكشف
    ذلك في فحص `storage`، ونسخة الليلة التالية كاملة.
  - النسخ في 02:15 يجعل هذا نادراً.

## الإعدادات (`apps/api/.env`)
| المتغير | الافتراضي | المعنى |
|---|---|---|
| `BACKUP_DIR` | `backups` | خارج مجلد الموقع، ولا يتداخل مع `STORAGE_DIR` أو `WEB_DIST_DIR` (يُرفض) |
| `BACKUP_KEEP_DAYS` | 14 | تُحذف النسخ الأقدم. أحدث نسخة تبقى دائماً |
| `MYSQLDUMP_PATH` | `mysqldump` | أداة التفريغ، أو `mariadb-dump` |
| `MYSQL_PATH` | `mysql` | أداة الاستعادة، أو `mariadb` |
| `BACKUP_VERIFY_DATABASE_URL` | (فارغ) | قاعدة **مؤقتة** لاختبار الاستعادة، واسمها يجب أن يحتوي `restore` أو `verify` |

`preflight` يتحقق أن `BACKUP_DIR` قابل للكتابة، وأن أداة التفريغ تعمل.

## الجدولة (Cron)
```
15 2 * * * cd /path/apps/api && node dist/jobs/cli.js backup >> logs/jobs.log 2>&1
```
- يطبع ملخصاً بصيغة JSON: المجلد، والملفات، والمحذوف.
- يخرج برمز 1 عند الفشل، فيصل بريد Cron.

## خارج الخادم (ADR-010 §4)
1. نسخ الاستضافة الخاصة: تأكد أنها مفعّلة في لوحة Hostinger.
2. **تنزيل أسبوعي يدوي** لأحدث مجلد `backup-…` إلى جهاز أو تخزين خارجي. كل ثلاثاء، ويُسجَّل في الجدول
   أدناه.
3. النسخ التلقائي إلى تخزين S3 مؤجَّل حتى يُختار مزود.

## اختبار الاستعادة الشهري (إلزامي)
```
node dist/jobs/cli.js backup-verify latest
```
- **الملفات:** يطابق كل ملف مع بصمته. **النسخة التالفة لا تُحمَّل أصلاً.**
- **التحميل:** يحمّل القاعدة في `BACKUP_VERIFY_DATABASE_URL` بعد حذفها وإعادة إنشائها. لا يقترب من
  القاعدة الحية، ويرفض إن كانت هي نفسها.
- **فحص المحتوى المستعاد:**
  - نفس الـ migrations؛
  - كل قيد مرحّل متوازن؛
  - أرصدة المخزون تساوي حركاته؛
  - كل ملف تشير إليه القاعدة موجود في `storage.zip`.
- **التنظيف:** يحذف القاعدة المؤقتة بعد الفحص. مع `--keep` تبقى للفحص اليدوي، وتُحذف بعدها باليد.
- **النتيجة:** يخرج برمز 1 إذا فشل أي فحص.

**السجل:** أضف سطراً بعد كل اختبار.

## الاستعادة الفعلية (عند كارثة)
**الهدف:** RPO = 24 ساعة كحد أقصى (نسخة يومية)، وRTO = بضع ساعات.

1. **أوقف التطبيق** من لوحة الاستضافة، **وأوقف أوامر Cron**، خصوصاً `einvoice-send`.
2. اختر النسخة، وشغّل عليها `backup-verify` أولاً.
3. **أنشئ قاعدة جديدة** من لوحة الاستضافة، ولا تكتب فوق القديمة. ثم حمّل التفريغ إليها:
   ```
   gunzip -c backup-…/database.sql.gz | mysql --defaults-extra-file=<ملف الخيارات> <القاعدة الجديدة>
   ```
4. **المرفقات:** انقل `STORAGE_DIR` الحالي جانباً، وفكّ `storage.zip` مكانه.
5. **غيّر `DATABASE_URL`** إلى القاعدة الجديدة، ثم شغّل `node dist/jobs/cli.js preflight`.
6. **شغّل التطبيق،** وتحقق: الدخول، وميزان المراجعة متوازن لشركة واحدة على الأقل، وظهور الشعار.
7. **أعد تشغيل أوامر Cron.**

### ⚠️ الفوترة الإلكترونية بعد استعادة نسخة قديمة
النسخة لا تعرف ما جرى بعد وقتها: المستندات المرحّلة، والفواتير التي قبلتها JoFotara، والعدادات (ICV).
- قبل تشغيل `einvoice-send`، **راجع مع المحاسب** ما أُرسل بعد `createdAt` في `manifest.json`.
- طريقة المعالجة قرار يحسمه المالك وفق وثيقة JoFotara الرسمية (`docs/decisions/0005-jofotara-fields.md`).
  لا تفترضها.
